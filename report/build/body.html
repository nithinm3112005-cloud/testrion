CHAPTER 1
INTRODUCTION

Machine-learning models now support decisions in finance, retail, manufacturing, transport and many other fields. Unlike ordinary software, a model does not fail by crashing or throwing an exception. It fails by being wrong: a loan model may reject deserving applicants, a price model may drift away from the market, or a classifier may behave well on average and badly for one group of people. Because the program keeps running, these failures are easy to miss. This project presents Testrion, a full-stack web platform that tests a machine-learning model automatically, in the same spirit as software testing, explains every problem it finds, decides whether the model is fit to be released, and repairs the problems that can be repaired.

1.1 Overview

Traditional software testing is built on deterministic expectations: if input X is given, output Y is expected. A machine-learning model has no such fixed oracle. Its behaviour is learned from data, so its quality depends on the data it saw, on how that data was cleaned, on the algorithm chosen and on the conditions under which it is used. A model can pass its own accuracy check and still crash when a field is missing, produce impossible predictions for unusual inputs, or treat different regions or age groups unequally [1], [4].

Testrion addresses this gap. A user uploads a tabular CSV file (or chooses one of the built-in sample datasets), selects the column to predict and selects a model. The platform detects whether the task is classification or regression, trains the model on a protected training split, and executes up to 24 automated tests grouped into five categories: data quality, model performance, robustness, reliability, and fairness with data-slice testing. The results are combined into a quality score, a grade and a deployment gate that approves or blocks the release of the model. When the gate blocks a model, an Auto-fix engine repairs the data pipeline, tunes the model and searches for a better algorithm, and then re-runs every test so that the improvement is demonstrated rather than assumed.

The platform is delivered as a React web application with a FastAPI back-end, accounts and per-user data isolation, a live drift-monitoring service, a Streamlit interface, a command-line deployment gate and a GitHub Actions workflow that runs the same checks on every code push. The chapters that follow describe the literature, the method, the models, the implementation, the datasets used and the measured results.

1.2 Background of the Study

Industrial experience shows that producing a trained model is only a small part of the effort needed to run machine learning reliably. Sculley et al. described the hidden technical debt of machine-learning systems, including entangled data dependencies and the difficulty of monitoring behaviour after deployment [2]. Breck et al. proposed the ML Test Score, a rubric of tests for data, model development, infrastructure and monitoring that a production system should satisfy [1]. Amershi et al. reported that teams building machine-learning applications face data-management, testing and model-quality challenges that differ from those of conventional software engineering [3]. A large survey by Zhang et al. organised the research on machine-learning testing into properties such as correctness, robustness, fairness and interpretability, and into testing components such as data, learning program and framework [4].

Three practical difficulties motivate automation. First, a single hold-out accuracy figure hides many failure modes: class imbalance can make a useless model look accurate, and leaked features can make a model look perfect. Second, the effort of running many checks by hand after every change is high, so checks are skipped. Third, the data seen in operation changes over time, so a model that was acceptable at release can silently degrade [15]. An automated and repeatable test suite, coupled with a clear release decision, addresses all three.

1.3 Problem Statement

Models are usually judged by one or two summary metrics on a single test set. This does not reveal whether the model crashes on missing values, behaves sensibly on unusual inputs, depends on a feature that will not exist in production, performs much worse for one group than another, or changes its predictions when features are merely rescaled. There is also no standard automatic procedure that turns the discovery of such a problem into a repair. The problem addressed by this project is to design, implement and evaluate a platform that (i) runs a broad and repeatable set of automated tests on any tabular classification or regression model, (ii) converts the results into an explicit, explainable release decision, (iii) automatically repairs the problems that can be repaired and verifies the repair, and (iv) keeps watching the model after release for data drift.

1.4 Existing System

In a typical student or small-team workflow, a model is trained in a notebook, evaluated with accuracy on a hold-out set and saved to disk. Continuous-integration services are normally used to test the program code, not the behaviour of the trained model. Open-source tools exist for individual parts of the problem, for example data validation, drift reports and fairness metrics, but they are separate libraries with their own interfaces; a team has to learn each of them, combine their outputs and decide by hand whether the model may be released [8].

Robust-engineering practice for software, such as unit tests, regression tests and metamorphic tests, is only partly transferable. Unit tests cannot say whether a prediction is correct, and an accuracy threshold alone cannot say whether the model is stable, fair or safe at the boundaries of its inputs. There is therefore a need for an integrated system that brings these checks together under one workflow, one score and one decision.

1.5 Objectives

The main objectives of the project are:

Objective 1: Automated test generation. Generate and run tests for data quality, prediction performance, robustness (including edge-case, adversarial and metamorphic tests), reliability and fairness without manual effort.

Objective 2: Deployment decision. Convert test outcomes into a quality score and a gate that blocks a release when hold-out accuracy (R² for regression) is below 85%, the demographic parity difference reaches 10%, a class is not detected, the data leaks the target or predictions are not reproducible.

Objective 3: Automatic problem solving. Diagnose failed tests and apply data repairs, hyper-parameter tuning and model search, then re-run all tests to prove the improvement, without ever using the hold-out test set to choose a model.

Objective 4: Monitoring and integration. Log predictions, detect data drift on live inputs, and run the same checks automatically on every code push through a CI workflow.

Objective 5: A usable, secure platform. Provide a web interface with accounts, dataset management, reports, a prediction playground, run comparison and model export, together with a measured demonstration of its performance.

1.6 Scope of the Project

The platform supports tabular classification and regression with twelve scikit-learn models (six classifiers and six regressors) on CSV data. An interactive run is capped at 6,000 rows for responsiveness, and a larger limit can be set for benchmarking. The evaluation uses five built-in datasets and six demonstration CSV files, of which two built-in datasets (Iris and Wine) are real public data and the remaining nine are synthetic datasets generated by the project code. The findings therefore illustrate how the platform behaves; they do not establish how a given real-world model would perform. Deep-learning models, images, text, time-series forecasting and formal differential-privacy guarantees are outside the scope of the current work, and the platform is designed for local, single-organisation use rather than as a hardened public service.

CHAPTER 2
LITERATURE SURVEY

This chapter reviews the research that informs Testrion: machine-learning testing in general, test oracles and metamorphic testing, data validation and leakage, robustness and adversarial examples, fairness testing, drift monitoring, production practices, and the model-selection techniques used by the Auto-fix engine. The purpose is to establish the ideas the platform builds on and to clarify how it differs from related work.

2.1 Machine Learning Testing

Zhang et al. surveyed more than a hundred papers on machine-learning testing and organised them by the property being tested (correctness, robustness, fairness, interpretability, efficiency), by the component tested (data, learning program, framework) and by the workflow stage (offline and online testing) [4]. Their survey shows that research is fragmented: most techniques test one property of one component. The ML Test Score by Breck et al. takes a complementary, engineering-oriented view: it lists 28 concrete tests and monitoring checks across data, model, infrastructure and monitoring, and suggests scoring a system by how many are implemented and automated [1]. Testrion adopts this practical stance. It implements a selected, fully automated subset (data validation, model-quality checks, robustness, reliability and fairness) and turns them into a single score and decision.

2.2 Test Oracles and Metamorphic Testing

A test oracle states what the correct output is. For machine learning the correct output is usually unknown, which is called the oracle problem. Metamorphic testing avoids it by checking relations between outputs of related inputs instead of the outputs themselves [5]. Xie et al. applied metamorphic testing to machine-learning classifiers and showed that relations such as permuting the order of training samples or rescaling features should leave predictions essentially unchanged, and that violations expose implementation or algorithmic weaknesses [6]. Testrion uses two such relations: unit-change invariance (features rescaled by different factors, the model re-trained, predictions compared) and training-order invariance (training rows shuffled, the model re-trained, predictions compared). Ribeiro et al. generalised the idea of behavioural testing in the CheckList methodology for language models, demonstrating that tests based on minimum functionality, invariance and directional expectation reveal failures that aggregate accuracy hides [7]; the same philosophy motivates the edge-case and perturbation tests in this work.

2.3 Data Validation and Leakage

Breck et al. described a production data-validation system that checks incoming data against a schema and flags anomalies before they reach training or serving, arguing that data errors are among the most common causes of model failure [8]. Kaufman et al. formalised target leakage, in which a feature carries information about the target that would not be available at prediction time, and showed that leakage produces models that look excellent in evaluation and fail in use [9]. Testrion therefore checks missing values, duplicates, constant columns, outliers, class balance, target skew and sample size, and applies a leakage detector: a depth-two decision tree is cross-validated on each feature alone, and a feature whose balanced accuracy alone reaches 0.96 is flagged (for regression, an absolute correlation of 0.98).

2.4 Robustness and Adversarial Examples

Goodfellow et al. showed that small, deliberately chosen perturbations of an input can change the prediction of an otherwise accurate model, and that this vulnerability is a property of the learned function rather than a rare accident [10]. Although their work concerned neural networks, the principle applies to tabular models: a robust model should not change its decision when each numeric feature moves by a small fraction of its natural spread. Testrion implements a model-agnostic adversarial test based on random-sign perturbation search, together with Gaussian-noise and missing-value stress tests, because the gradients required by gradient-based attacks are not available for tree ensembles and nearest-neighbour models.

2.5 Fairness Testing

Several formal definitions of fairness exist. Dwork et al. introduced the idea that similar individuals should be treated similarly [12]. Feldman et al. connected the legal notion of disparate impact to measurable differences in outcome rates between groups [13]. Hardt et al. proposed equality of opportunity, which compares true-positive rates across groups [11]. Mehrabi et al. surveyed the sources of bias and the many fairness definitions and stressed that they can conflict and that no single metric certifies a model as fair [14]. Testrion implements the demographic parity difference required by the project specification, defined as the largest gap in predicted-outcome rate between groups of a protected attribute. It reports slice-level accuracy so that weak groups can be seen, and it states clearly that demographic parity is one criterion and not a proof of fairness.

2.6 Drift and Monitoring

Gama et al. surveyed concept drift: the statistical relationship between inputs and outputs, or the distribution of the inputs themselves, can change after deployment, and a model must be monitored to notice this [15]. A widely used industrial measure of distribution change is the Population Stability Index (PSI), common in credit scoring, where values below 0.1 indicate stability and values above 0.25 indicate a significant shift [16]. Testrion applies PSI in two places: between the training and test splits as a reliability test, and between the training data and logged live predictions in the monitoring service.

2.7 Machine Learning in Production: Technical Debt and CI/CD

Sculley et al. argued that machine-learning systems accumulate technical debt faster than ordinary software because data dependencies, feedback loops and configuration are hard to see and test [2], and Amershi et al. observed that teams need new testing and deployment practices [3]. A practical consequence is that the model itself, and not only its code, should pass automated checks before a release. Testrion supports this with a GitHub Actions workflow that runs a pytest suite and a command-line deployment gate on every push or pull request; the gate returns a non-zero exit code when the model is blocked, so that the pipeline fails before deployment.

2.8 Model Selection and Hyper-parameter Search

Cross-validation estimates generalisation by repeatedly training on part of the data and validating on the rest; Kohavi's study found k-fold cross-validation to be a reliable and low-variance way to estimate accuracy and select models [19]. Bergstra and Bengio showed that random search over a hyper-parameter space is often as effective as an exhaustive grid at a much lower cost [18], which motivates the randomised search used in Stage 2 of the Auto-fix engine. The candidate algorithms compared by the engine are classical, well-understood models implemented in scikit-learn [17]: logistic regression, decision trees [22], random forests [20], gradient boosting [21], support-vector machines [23], nearest neighbours [24] and ridge regression [25]. Imbalanced classes are handled with class weights or random oversampling, in line with the survey by He and Garcia [26].

2.9 Research Gap

The literature provides strong individual techniques, namely metamorphic relations, data validation, adversarial examples, fairness metrics and drift statistics, but they are normally studied and implemented separately. Industrial rubrics such as the ML Test Score list what should be tested without providing an executable implementation that produces a decision. Existing tools report problems but rarely repair them or prove that a repair worked. The gap addressed here is an integrated, executable and explainable workflow that (i) runs a broad automated suite on any tabular model, (ii) converts it into a deployment decision under explicit thresholds, (iii) repairs failures and verifies the repair with a strict train, validation and test discipline, and (iv) connects the result to CI and live monitoring. CHAPTER 3
METHODOLOGY AND PROPOSED SYSTEM

This chapter explains the workflow implemented in Testrion. The pipeline starts with a dataset, validates it and detects the task, prepares the data with a protected hold-out split, trains the chosen model, executes the automated test suite, converts the outcomes into a score and a deployment decision, and, when requested, diagnoses and repairs the problems before re-testing. A separate monitoring component watches live predictions after release. The chapter also describes in detail every dataset used in the project.

3.1 System Workflow

The workflow of a single run is shown in Figure 3.1. The user supplies a CSV file or selects a built-in sample, chooses the target column and the model, and optionally switches on pipeline options such as imputation, scaling or class balancing. The server validates the request, detects the task, prepares the data and trains the model. The test suite then evaluates data quality, model performance, robustness, reliability and fairness. The results are stored in the database, shown in the web interface and used to compute the deployment decision. If problems exist, the Auto-fix engine produces a second run in which the repairs were applied, and both runs are kept so they can be compared.

3.2 Datasets Used

The project uses eleven datasets: five built into the application and six demonstration CSV files that are uploaded through the interface. Two of them (Iris and Wine) are real public datasets distributed with scikit-learn [17], [27], [28]; the other nine are synthetic datasets produced by seeded generators in the project code, so every run is reproducible. Synthetic data was chosen deliberately: it allows realistic problems (missing values, duplicates, outliers, class imbalance, leakage, biased groups) to be injected in known amounts, so that the platform's ability to find and repair them can be demonstrated and verified. This also means that the accuracy figures reported in this document describe the behaviour of the platform on these datasets and must not be read as the expected accuracy of a real application. 3.2.1 House Price Prediction (primary dataset)

The house-price dataset is the demonstration dataset named in the project specification. It is a synthetic regression dataset of 1,640 rows and 9 columns in which the price of a house, in lakhs of rupees, is predicted from its area, the number of bedrooms and bathrooms, the year of construction, the distance to the city centre, the number of garage spaces, the region of the city and the property type. The price is generated from a base value that grows with area, rooms, garage spaces and newness and falls with distance from the city, multiplied by a regional factor (the West and Central regions are more expensive) and a property-type factor (villas cost more than apartments), and then a small log-normal noise term is applied. The target has a mean of 118.9 lakhs, a median of 112.7, a range of 26.8 to 343.6 and a skewness of 0.98.

The generator injects realistic data problems on purpose: missing values in the area (5%), distance (6%) and region (3%) columns, which gives 235 missing cells in total (1.6% of all cells); twelve data-entry outliers in which the area is several times too large; and 40 duplicated rows. 3.2.2 Iris Flowers

Iris is the classic multi-class benchmark introduced by Fisher in 1936 [27] and distributed through the UCI repository [28] and scikit-learn. It contains 150 flowers, four numeric measurements (sepal length and width, petal length and width) and a balanced three-class target (setosa, versicolor, virginica; 50 flowers each). It contains one duplicated row and no missing values. In this project it serves as a clean, small, real dataset on which the platform is expected to report few problems, and it shows that Auto-fix does not invent improvements where none are needed.

3.2.3 Wine Cultivars

The Wine dataset records 13 chemical measurements (for example alcohol, malic acid, flavanoids, colour intensity and proline) for 178 wines grown by three cultivars [28]. The classes are moderately imbalanced (71, 59 and 48 wines). The features are measured on very different scales (proline is in the hundreds while hue is near one), which makes the dataset a good test of scale sensitivity: distance-based and kernel models such as support-vector machines perform poorly on the raw values and well after standardisation.

The customer-churn dataset is a synthetic binary classification problem with 1,890 rows and 8 columns in which the target says whether a telecom customer leaves (Yes) or stays (No). The dataset is imbalanced (about 28% churners), contains 319 missing cells, 90 duplicated rows, a constant column (country_code) and a feature on a very large scale (total_charges). 3.2.7 Dataset Handling in the Application

  • The Datasets page lists every dataset with its origin (real, synthetic or uploaded), size and tags, and offers a preview with a data dictionary and a CSV download.
  • Uploaded files must be CSV, at most 10 MB, with at least 20 rows and 2 columns. Each uploaded file belongs to one user and is never shown to others.
  • The target selector marks which columns are valid targets: a column with 2 to 30 categories is a classification target, and a numeric column with more than 20 distinct values is a regression target; other columns are disabled.
  • Columns that look like identifiers (text columns with more than 50 distinct values that are also more than 30% of the rows) are dropped automatically and reported.
  • Interactive runs use at most 6,000 randomly sampled rows so that results appear within seconds; the limit can be raised for benchmarking.

3.3 Data Preprocessing

Preprocessing is implemented as a scikit-learn ColumnTransformer placed in front of the model, so that exactly the same transformation is applied during training, testing, prediction and export. Numeric columns can pass through an optional median imputer and an optional scaler (standardisation or a robust median/IQR scaler). Categorical columns can pass through an optional most-frequent imputer and are always one-hot encoded, with unseen categories ignored at prediction time. When imputation is switched off, rows containing missing values are dropped before training, which is the naive behaviour that the tests are designed to expose. All preprocessing statistics are learned on the training portion only.

Additional data-preparation options, which the Auto-fix engine can switch on, are removal of duplicate rows, removal of constant columns, removal of named columns (for example a leaking or protected column, which is still kept aside so it can be audited), balancing of classes by class weights or random oversampling, and a log(1+y) transformation of a skewed non-negative regression target.

3.4 Data Splitting and Validation Protocol

Every model is evaluated with a strict three-part protocol, shown in Figure 3.3. The prepared rows are divided into a 75% training portion and a 25% hold-out test portion with a fixed random seed (stratified by class for classification). The test portion is never used to fit a model, to tune a hyper-parameter or to choose between algorithms. The validation score is obtained by k-fold cross-validation inside the training portion only [19], and it is the only score the Auto-fix engine uses to decide whether a tuning or model change is kept. The test portion is used for the final report and for the tests that need unseen data. After evaluation, the exported model (model.pkl) and the playground model are re-trained on all rows, as is standard practice before deployment.

One detail deserves mention. The diagnosis of problems (which tests failed) is read from the test results, which include test-set measurements such as the overfitting gap. The selection of hyper-parameters and algorithms, however, depends on validation scores only, so the hold-out set cannot be overfitted through model selection.

3.5 Feature Representation

Features are the columns of the CSV file other than the target. Numeric features are used as they are (optionally imputed and scaled); categorical features are expanded into binary indicator columns. The number of encoded features therefore depends on the cardinality of the categorical columns. Protected attributes such as gender, age and region are detected from column names: a column whose name contains a token such as gender, sex, age, region, race, religion, caste or marital is audited, except where the name shows that it describes an object or a duration (for example account_age_days or floor_area_sqft). The user can mark any other column as protected in the advanced options. Numeric protected attributes such as age are divided into three quantile bands for slicing.

3.6 Proposed System Architecture

The system consists of a React web application, a FastAPI server, a testing engine, an Auto-fix engine, a model registry and a SQLite database, with an optional Streamlit interface and a GitHub Actions workflow around them. The detailed architecture, the modules, the database schema and the API are described in Chapter 5, and the architecture is shown in Figure 5.1. The important design decision is that the testing engine and the Auto-fix engine are ordinary Python modules that do not depend on the web server, so the same code runs in the web application, in the command-line gate, in the pytest suite and in the Streamlit interface.

Four of these tests implement requirements named in the project specification and are described in more detail below.

Edge-case generation. For up to eight numeric columns the test builds copies of five test rows in which one column at a time is replaced by its training minimum, its maximum, zero, a value ten ranges beyond the maximum, or a null value; for up to four categorical columns it substitutes an unseen category, a string of special characters (including quotes and markup), an empty string or a null. The model is asked to predict all of these rows; a crash, a non-finite value or a regression value far outside the plausible range counts as a failure.

Adversarial perturbation. A random sample of up to 250 test rows is perturbed eight times; in each perturbation every numeric feature moves up or down by a random sign times a fixed fraction of that feature's training standard deviation. A row is stable if its prediction (class, or value within 20% for regression) never changes. The fraction of stable rows is the score.

Data-slice testing. The test set is split by each protected attribute (or, when none is found, by up to two low-cardinality categorical columns), the accuracy or the percentage error is computed per slice with at least 15 rows, and the spread between slices is compared with the threshold.

Demographic parity. For classification the parity difference of a protected attribute is the largest, over predicted classes, of the gap between the highest and lowest rate at which the class is predicted in a group. For regression, where outcomes are numbers, the corresponding measure is the group bias, |mean prediction − mean actual| divided by the mean actual value, taken per group. The attribute with the worst value is reported.

3.8 Scoring and Deployment Gate

Each test contributes one point when passed, half a point as a warning and none when failed; skipped tests are ignored. The category scores are combined with weights of 2.0 for Model Performance, 1.5 for Robustness and for Fairness & Slices, and 1.0 for Data Quality and for Reliability, giving a quality score from 0 to 100 and a grade (A ≥ 90, B ≥ 80, C ≥ 70, D ≥ 55, otherwise F). The score is a convenient summary; the release decision is made by the deployment gate, which is independent of the score (Figure 3.4).

The gate requires: (1) hold-out accuracy of at least 85% for classification or hold-out R² of at least 0.85 for regression, because accuracy is not a regression metric and R² is its natural equivalent; (2) a demographic parity difference below 10% whenever a protected attribute is present and large enough to evaluate; (3) for classification, a worst-class recall that is not a failure, so that a model cannot be approved merely because it predicts the majority class; (4) no target leakage; and (5) reproducible predictions. If any check fails, the gate reports BLOCKED and names the check; otherwise it reports APPROVED.

3.9 Auto-Fix Engine

The Auto-fix engine is the problem-solving part of the platform. It reads the failed and warning tests of a run, applies the matching repairs, re-runs the full suite and reports exactly what changed (Figure 3.5). It works in three stages. Stage 1 repairs the data pipeline and is always kept, because it removes real defects: Table 3.7 lists the mapping from failed tests to repairs. Stage 2 tunes hyper-parameters with a randomised search over a small regularisation-friendly grid, using at most eight candidates and three-fold cross-validation on the training portion only [18]; the result is kept only if the validation score does not decrease. Stage 3 compares alternative algorithms by cross-validated score on the training portion (logistic regression, random forest and gradient boosting, plus a support-vector machine for small data, for classification; ridge regression, random forest and gradient boosting for regression) and switches only if a candidate is clearly better and the validation score of the new run improves.

3.10 Live Monitoring

After a model is accepted, it can be used through the prediction playground or the API. Every prediction is logged with its inputs, output and latency. The monitoring service compares the logged inputs with a reference sample of the training data using the Population Stability Index for each feature [15], [16]. A feature with PSI below 0.10 is stable, between 0.10 and 0.25 is a warning and above 0.25 indicates drift; the overall status becomes DRIFT DETECTED when any feature exceeds 0.25 and at least 30 predictions have been logged. For demonstration the service can replay training-like traffic, normal or deliberately shifted, through the live model. The monitoring page also reports the average and 95th-percentile prediction latency and the time taken to compute the drift verdict.

3.11 CI/CD Integration

The repository contains a GitHub Actions workflow that is triggered on every push and pull request [34]. It installs the dependencies on Ubuntu 22.04 with Python 3.10, runs the 11 pytest tests, runs the command-line deployment gate on the house-price model with imputation and de-duplication enabled, and uploads the JSON test report as an artefact. The gate script exits with status 1 when the gate is blocked, which makes the workflow fail, so that a model or a code change that breaks the acceptance conditions cannot pass unnoticed. This chapter describes the models that Testrion trains and tests and the metrics used to judge them. Testrion does not propose a new learning algorithm; its contribution is the testing and repair of models. It therefore uses well-known, interpretable scikit-learn models [17] so that the behaviour of the tests can be studied on algorithms with different strengths and weaknesses: linear and non-linear, scale-sensitive and scale-insensitive, high-bias and high-variance.

4.2 Logistic Regression

Logistic regression models the probability that an input belongs to the positive class as the logistic function of a linear combination of the features [17]. For a feature vector x with weights w and bias b,

p(y = 1 | x) = σ(wᵀx + b), σ(z) = 1 / (1 + e⁻ᶻ)
(4.1)

The weights are found by minimising the regularised binary cross-entropy (log) loss,

L(w) = −(1/n) Σ [ yᵢ log pᵢ + (1 − yᵢ) log(1 − pᵢ) ] + (1 / 2C)‖w‖²
(4.2)

where C controls the strength of regularisation. Multi-class problems are handled by the multinomial extension. Because the penalty and the optimiser treat all weights alike, logistic regression is sensitive to feature scale, which the unit-change test reveals and the standardisation repair removes. It is used in the demonstration as a fast, stable baseline and, after Auto-fix, as the chosen model for the churn, credit-default and loan-approval datasets.

4.3 Decision Trees

A decision tree splits the feature space recursively with axis-aligned thresholds, choosing at each node the split that most reduces impurity [22]. For classification the Gini impurity of a node with class proportions p_k is

G = 1 − Σₖ pₖ²
(4.3)

and for regression the splits reduce the mean squared error. Trees need no feature scaling and handle mixed data naturally, but an unconstrained tree memorises the training data, which appears in the overfitting-gap test as a training score near 1.0 and a much lower test score. Limiting max_depth and min_samples_leaf, as the tuning stage does, regularises the tree.

4.4 Random Forest

A random forest averages many decision trees, each trained on a bootstrap sample of the rows and a random subset of features at every split [20]. Averaging reduces variance, so forests are accurate and robust on tabular data. For regression the prediction is the mean of the trees, for classification the majority vote. The platform uses forests of 120 trees by default and searches 100 or 200 trees, depths of 4, 8 or unlimited (6, 12 or unlimited for regression) and leaf sizes of 1, 3 or 5 during tuning.

4.5 Gradient Boosting

Gradient boosting builds trees sequentially, each new tree fitted to the negative gradient of the loss with respect to the current predictions [21]:

Fₘ(x) = Fₘ₋₁(x) + ν · hₘ(x)
(4.4)

where hₘ is the m-th shallow tree and ν the learning rate. Boosting often gives the highest accuracy on structured data, but without regularisation (a small depth, a modest learning rate and a limited number of trees) it can overfit. In the house-price experiment the Auto-fix model search selected gradient boosting for the regression problem.

4.6 K-Nearest Neighbours

The k-nearest-neighbours rule predicts the majority class (or the mean value) of the k training points closest to the query point [24], using Euclidean distance on the encoded features:

d(x, x′) = √ Σⱼ (xⱼ − x′ⱼ)²
(4.5)

Since the distance is dominated by features with large numeric ranges, KNN is the most scale-sensitive model in the registry. It fails the unit-change test unless the features are standardised and is therefore a useful demonstration of the metamorphic test.

4.7 Support Vector Machine

A support-vector machine finds the decision boundary that maximises the margin between classes, and with the radial-basis-function kernel it can represent non-linear boundaries [23]:

K(x, x′) = exp( −γ ‖x − x′‖² )
(4.6)

The kernel depends on distances, so the SVM requires standardised inputs. On the unscaled Wine dataset it classifies only 71% of the test wines correctly, and after standardisation 98%, which is the clearest single example of a repair in the experiments (Chapter 7).

4.8 Linear and Ridge Regression

Linear regression predicts a number as a weighted sum of the features and minimises the squared error. Ridge regression adds an L2 penalty on the weights, which stabilises the solution when features are correlated [25]:

ŵ = argmin_w ‖y − Xw‖² + α‖w‖²
(4.7)

Linear models are the natural baseline for the house-price problem. They cannot represent the multiplicative effect of region and property type on price, so their hold-out R² is limited, and they can predict negative prices for small houses, which the valid-predictions test detects. Training on log(1 + price), one of the Auto-fix repairs, converts these multiplicative effects into additive ones and guarantees non-negative predictions.

4.10 Evaluation Metrics

Let TP, TN, FP and FN denote true positives, true negatives, false positives and false negatives of a binary problem. The metrics used for classification are

Accuracy = (TP + TN) / (TP + TN + FP + FN)
(4.8)
Precision = TP / (TP + FP)
(4.9)
Recall = TP / (TP + FN)
(4.10)
F1 = 2 · Precision · Recall / (Precision + Recall)
(4.11)

For problems with more than two classes the precision, recall and F1-score are computed per class and averaged. The macro average treats every class equally and is the quantity used by the F1 test; the weighted average weights each class by its number of test rows. The worst-class recall, the smallest recall over all classes, protects against a model that ignores a rare class. For regression the metrics are

R² = 1 − Σ(yᵢ − ŷᵢ)² / Σ(yᵢ − ȳ)²
(4.12)
RMSE = √[ (1/n) Σ(yᵢ − ŷᵢ)² ], MAE = (1/n) Σ|yᵢ − ŷᵢ|
(4.13)
MAPE = (1/n) Σ |yᵢ − ŷᵢ| / |yᵢ|
(4.14)

Reliability and fairness use two further quantities. The Population Stability Index between a reference distribution with bin shares eᵢ and a current distribution with shares aᵢ is

PSI = Σᵢ (aᵢ − eᵢ) · ln(aᵢ / eᵢ)
(4.15)

and the demographic parity difference of a protected attribute with groups g is

DPD = maxₖ ( max_g P(ŷ = k | g) − min_g P(ŷ = k | g) )
(4.16)

where P(ŷ = k | g) is the rate at which class k is predicted within group g. These definitions are used consistently by the testing engine, the web interface and the Streamlit application.

5.7 Authentication and Data Isolation

Passwords are never stored. At sign-up a random 16-byte salt is generated and the password is hashed with PBKDF2-HMAC-SHA256 and 200,000 iterations [31]; at sign-in the hash is recomputed and compared in constant time, and the same error message is returned for an unknown e-mail address and for a wrong password. A successful sign-in creates a random 32-byte URL-safe token that is stored in the sessions table and expires after seven days. Every protected endpoint resolves the token to a user and filters all data by that user, so one user cannot read, run or delete another user's datasets, runs or predictions; this behaviour is verified by an automated test. User-supplied pipeline options are validated against a whitelist before use, uploaded files are restricted to CSV files of at most 10 MB, and model export uses the standard Python pickle format [37] (a pickle file must only be loaded from a trusted source).

CHAPTER 6
ADDRESSING COMPLEX ENGINEERING PROBLEMS WITH SOCIAL IMPACT

This project addresses a complex engineering problem because testing a machine-learning model involves several goals that interact and can conflict. A model must be accurate, but accuracy alone is misleading when classes are imbalanced or features leak the answer. A model must be robust, but robustness to noise is different from robustness to missing values or to unusual inputs. A model should be fair to groups of people, but fairness can reduce accuracy and the available fairness definitions can disagree. A repair must improve the model, but a repair chosen with the test data would make the reported accuracy dishonest. These objectives cannot be assessed with one metric, so the project combines test design, statistical measurement, automatic repair, software engineering and explicit reporting of limits.

6.1 Introduction: Engineering Complexity

The difficulty appears at every layer. At the data layer the platform must accept arbitrary CSV files and still decide, without human help, which column is a valid target, which columns are identifiers and which attributes concern people. At the learning layer it must support linear, tree-based, distance-based and kernel models, whose weaknesses differ: the same preprocessing that rescues a support-vector machine is irrelevant for a random forest. At the testing layer each test needs thresholds that are strict enough to catch real problems and tolerant enough not to raise false alarms on small datasets; for example, the drift statistic is noisy on a 38-row test set, so its thresholds scale with sample size. At the decision layer the gate must refuse a model that merely predicts the majority class even though its accuracy looks high. At the repair layer the engine must separate diagnosis, which may use test results, from selection, which may use validation scores only. Finally, at the software layer the system must be reproducible, secure enough for local use and fast enough for interactive work: the measured benchmarks in Chapter 7 show a full 24-test run on one million records in 22 seconds with a linear model.

6.2 Social Impact

Automated, repeatable testing of models can reduce the chance that an unreliable or unfair model reaches users. The fairness and slice tests make differences between groups visible before release instead of after complaints. The leakage test prevents a model that looks perfect in evaluation from being deployed on information that will not exist in practice, which in lending or fraud detection can mean wrongly approved or wrongly refused customers. The live drift monitor helps to notice that the world has changed. Because the platform is free, runs on a laptop and explains every finding in plain language, it can also be used for teaching how responsible machine-learning practice looks in a working tool.

The potential impact must be described carefully. Testrion tests the properties it implements, on the data it is given. A passed gate is evidence, not a guarantee: it does not prove that a model is correct for every input, that it is fair in every sense or that it is secure against a determined attacker. Demographic parity is only one fairness criterion, and some of the sample data are synthetic. The tool supports good decisions; it does not replace human responsibility for them.

7.9 Limitations and Interpretation

The results are limited in several ways that should be stated plainly. Nine of the eleven datasets are synthetic, so the accuracy values show how the platform behaves when problems of known size are present, not what a real application would achieve. The thresholds (for example 85% accuracy or R² and a 10% parity difference) come from the project specification and are reasonable defaults, not universal truths; demographic parity in particular is one criterion among several. The robustness tests sample perturbations at random, so they can miss a worst-case attack. The benchmarks were measured on one machine, and the one-million-record figure is for a linear model. Auto-fix improves what the tests measure; it cannot add information that the data do not contain, as the student-grades file shows. Finally, the GitHub Actions workflow and the Dockerfile are provided but have not been executed on GitHub or in Docker from the development machine; the equivalent commands were run locally.

CHAPTER 8
CONCLUSION AND FUTURE WORK

8.1 Conclusion

This project designed, implemented and evaluated Testrion, a platform for automated software testing and problem solving of machine-learning models. The platform accepts any tabular CSV dataset, detects the task, trains one of twelve scikit-learn models and runs up to 24 automated tests in five categories. A deployment gate converts the results into an explicit decision, and a three-stage Auto-fix engine repairs the data pipeline, tunes the model and searches for a better algorithm, always verifying the result by re-running the full suite. A strict protocol keeps the hold-out test set out of every training, tuning and selection decision.

On the house-price dataset, the baseline linear regression scored 75.0 and was blocked by the gate; after Auto-fix the gradient-boosting model scored 97.1, reached a hold-out R² of 0.862 and was approved. On the loan-approval file, removing protected attributes that caused a parity gap moved the score from 64.8 to 97.7. On the Credit and Fraud files the platform detected target leakage and replaced an inflated accuracy with an honest one, and on the student-grades file it correctly refused to approve a model that could not reach the threshold. Measured on one Apple M5 laptop, the full suite processed one million records in 22 seconds with a linear model, one hundred models were tested concurrently in 41 seconds, and drift was detected on live predictions in 11 milliseconds.

These results indicate that integrating data validation, behavioural testing, fairness checks, a release gate, automatic repair and monitoring in one reproducible workflow is practical and fast enough for interactive use. They do not show that a passed gate guarantees correct behaviour in production, that demographic parity alone makes a model fair, or that the platform would give the same results on real datasets, since nine of the eleven datasets are synthetic. The GitHub Actions workflow and the Dockerfile are provided but were not executed on GitHub or in Docker from the development machine.

8.2 Future Work

Several extensions would strengthen the work:

  1. Evaluate the platform on real, publicly available datasets such as a real house-price or credit dataset, and report results with confidence intervals over repeated splits.
  2. Add further fairness definitions, such as equality of opportunity (equal true-positive rates) and calibration within groups, and let the user choose the criterion of the gate.
  3. Add more robustness tests, including distribution-shift scenarios, label noise and gradient-based adversarial attacks for models that expose gradients.
  4. Extend support to deep-learning, image, text and time-series models with suitable adapters and tests.
  5. Add explanation methods, such as SHAP values, to the report to help diagnose why a test failed.
  6. Harden the platform for multi-user deployment: password reset and e-mail verification, login rate limiting, a production web server and database, and sandboxing of uploaded models.
  7. Run the benchmark suite on larger machines and with tree ensembles at one million rows, and publish the measurements together with the hardware.
  8. Integrate the monitoring service with an alerting channel and with automatic retraining pipelines.

9.1 Purpose of the Workflow

The workflow is organised so that data preparation, training, testing, scoring, repair and monitoring can be inspected independently. This matters because a change in preprocessing alters the model inputs, a change in the model alters every test, and a change in the thresholds alters the decision even when the model is unchanged. Reproducible experimentation therefore requires a stable configuration, a fixed random seed and a record of the artefacts produced at each stage. In Testrion each run stores its complete configuration (model, target, pipeline options, hyper-parameters, seed) inside the result, so any run can be repeated and any two runs can be compared.

A run starts with a validated dataset. The training portion is used to learn preprocessing statistics, which are then applied unchanged to the test portion. The model is trained, the tests are executed and the results are scored. If the user starts Auto-fix, the engine reads the failed tests of the stored run, creates a new configuration, trains and tests again and stores a second run that points to the first through its parent identifier, so the history shows exactly what was changed and why.

10.1 Sequence of a Test Run and of Auto-Fix

Figure 10.1 shows the interaction between the browser, the server, the engines and the database when a test run is requested and then repaired. The browser sends the dataset identifier, the target and the model; the server checks ownership and task, calls the testing engine, stores the result and returns it. 10.2 Algorithm 1: Running the Test Suite

run_suite(data, target, model, config):
    task <- detect_task(data, target); check model.task == task
    df, audit <- prepare(data, target, config)          # cap rows, drop ids, repair options
    train, test <- split(df, 75% / 25%, seed = 42)
    pipeline <- build_model(model, config)               # impute / scale / encode + estimator
    fit pipeline on train
    tests <- []
    tests += data_quality_tests(df)                      # missing, duplicates, balance/skew,
                                                         # constants, outliers, leakage, size
    tests += performance_tests(pipeline, train, test)    # hold-out, CV on train, gap, recall
    tests += robustness_tests(pipeline, train, test)     # noise, blanks, unit change, order,
                                                         # edge cases, adversarial
    tests += reliability_tests(pipeline, train, test)    # reproducibility, PSI, latency
    tests += slice_and_fairness_tests(test, audit)       # slices, demographic parity
    score <- weighted_score(tests); gate <- deployment_gate(tests)
    return {tests, score, grade, gate, metrics, profile, config}

autofix(data, target, model, original):
    cfg <- original.config
    # Stage 1 - pipeline repair (always kept)
    for each failed or warned test in original.tests:
        apply the matching repair to cfg          # see the repair table in Chapter 3
    result <- run_suite(data, target, model, cfg)
    # Stage 2 - hyper-parameter search (kept only if validation score does not drop)
    if model-level tests still fail:
        params <- randomised_search(grid[model], cv = 3, on = train only, n_iter <= 8)
        candidate <- run_suite(data, target, model, cfg + params)
        if candidate.cv_score >= result.cv_score: result <- candidate
    # Stage 3 - algorithm search (kept only if validation score improves)
    if quality tests still fail:
        scores <- {m: cv_score(m, train only) for m in candidates[task]}
        best <- argmax(scores)
        if scores[best] > scores[model] + 0.01:
            candidate <- run_suite(data, target, best, cfg)
            if candidate.cv_score > result.cv_score: result, model <- candidate, best
    return result, steps, before_after_comparison

10.4 Algorithm 3: Edge-Case and Adversarial Tests

Five test rows are copied many times; in each copy one numeric column is set to its training minimum, maximum, zero, maximum plus ten ranges, or null, or one categorical column is set to an unseen category, special characters, an empty string or null. Rows that make the model raise an error or return a non-finite or implausible value count as failures. For the adversarial test, up to 250 test rows are perturbed eight times by adding to every numeric feature a random sign times ε times its training standard deviation (ε = 0.15, or 0.10 for regression); a row is stable if its class never changes (regression: never changes by more than 20%), and the fraction of stable rows is reported.

10.5 Algorithm 4: Live Drift Monitoring

Every prediction is logged with its inputs and latency. A reference sample of up to 2,000 training rows is drawn; for each numeric feature eight quantile bins are formed from the reference data and the shares of reference and live values in each bin are compared (for categorical features, the category shares). The PSI of each feature (Equation 4.15) is compared with 0.10 and 0.25, and DRIFT DETECTED is reported when any feature exceeds 0.25 and at least 30 predictions are logged, together with the time taken to compute the verdict.

11.1 Confusion-Matrix Terms

The confusion matrix separates correct and incorrect predictions by class. For a binary problem, one class is chosen as positive. A true positive is a positive record predicted as positive, a false negative is a positive record predicted as negative, a true negative is a negative record predicted as negative, and a false positive is a negative record predicted as positive. In the customer-churn example below, "Yes" (the customer leaves) is the positive class (Table 11.1).

(11.1)

(11.2)

For regression the same principle applies: the hold-out errors of the house-price model are summarised by the RMSE, the MAE and the mean absolute percentage error, and the comparison table in the report lists actual and predicted prices row by row.

11.3 Interpreting Metrics Together

No single metric captures the behaviour of a model. Accuracy is influenced by the class distribution: in the fraud file only about 7% of the transactions are fraudulent, so a model that never predicts fraud would be about 93% accurate, which is why the gate also checks the worst-class recall. Precision tells how reliable a positive prediction is, and recall tells how many of the real positives are found; a conservative model can have high precision and low recall. For regression, R² says how much of the variance is explained but not how large the errors are in real units, so the RMSE, the MAE and the percentage error are reported as well. The cross-validation score and the gap between training and test scores show whether the model is stable and whether it overfits.

11.4 Limits of the Drift Statistic and of the Quality Score

The Population Stability Index is sensitive to the number of bins and to the sample size: on small samples it is noisy even without any real shift, which is why the thresholds of the train/test drift test grow with the expected noise level. It examines each feature separately and cannot detect a change in the relationship between the features and the target. The quality score is a convenient weighted summary, but it depends on the chosen weights; two models with the same score can have different weaknesses, and the deployment gate, not the score, makes the release decision.

CHAPTER 13
THREAT MODEL AND SECURITY DISCUSSION

13.1 Assets and Adversaries

Two sets of assets must be considered. For the platform, the assets are the user accounts, the uploaded datasets, the stored runs and trained models, and the integrity of the verdicts. For the models under test, the assets are the correctness, fairness and availability of their predictions. The adversaries considered are an unauthorised user trying to read another user's data, a user who uploads a malformed or hostile file, a data provider whose data contain leakage or bias, and a deployer whose model drifts away from the data it was trained on.

13.3 Testing Is Not a Complete Guarantee

A passed test shows the absence of one specific problem under one specific stress; it does not prove the absence of other problems. The thresholds are defaults from the specification. Random perturbation can miss rare worst cases, the leakage detector looks at one feature at a time and cannot find leakage that needs a combination of features, and demographic parity can be satisfied by a model that is unfair in another sense. The deployment gate should therefore be read as a necessary check before release and not as a certificate of correctness.

13.4 Privacy and Integrity Are Different Goals

Testrion focuses on integrity and quality of models. It does not provide differential privacy or secure aggregation, and it does not claim to. Datasets uploaded by a user are stored unencrypted in the local project folder, so the machine that runs the platform must be protected like any other place that holds the data. Passwords are the only secrets stored, and they are stored as salted hashes.

13.5 Deployment Boundary

The application was developed and tested locally on macOS and is designed for single-organisation use. It should not be described as a hardened public service without further work on rate limiting, password recovery, transport security (HTTPS termination), a production database and web server, resource limits, logging and monitoring of the platform itself, and a security review. The trust boundary lies between the browser, the API server, the Python engines, the dataset files and the exported model files.
